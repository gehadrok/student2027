# ADR-0007: Persistence Behind IDataSource Abstraction (SQLite Initial)

**Status:** Accepted
**Date:** 2026-08-01

## Context

Early repositories called `getRealmDB()` directly and one repository imported the SQLite engine directly (violations documented in `docs/architecture-compliance-report.md`). The platform needs a generic, swappable persistence abstraction so repositories depend on an interface, not a concrete engine.

Phase 1.1 established `src/core/datasource/IDataSource.ts`, `SQLiteDataSource.ts`, `DataSourceFactory.ts`, and `UnitOfWork.ts`. The data layer is SQLite-based today.

## Decision

Adopt persistence behind the **`IDataSource` abstraction** with SQLite as the initial provider:

- Repositories receive `IDataSource` via constructor injection; they never instantiate or import the concrete engine.
- Screens never touch `IDataSource` or `getRealmDB()`; they consume services.
- `DataSourceFactory` is the singleton entry point.
- `UnitOfWork` provides transactional boundaries.
- The abstraction allows a future provider change (e.g., PostgreSQL) without repository changes.

## Consequences

**Positive:**

- Clean dependency direction and testability.
- Engine swap possible behind the interface.
- Compliance with the constitution's layered access rules.

**Negative:**

- SQLite-specific capabilities must stay behind the interface.

## Rationale

This records the already-implemented Phase 1.1/1.2 data-layer compliance decision and extends it as the permanent persistence contract for all future domain infrastructure.
