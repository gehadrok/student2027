# ADR-0003: Event-Driven Integration via Outbox/Inbox

**Status:** Accepted
**Date:** 2026-08-01

## Context

Cross-context operations (enrollment, promotion, transfer, graduation, attendance, assessment, certificate, fee payment, library, notifications, reporting, AI) require reliable propagation of facts between contexts. Direct cross-context repository access and synchronous multi-context transactions were forbidden by the Bounded Context Map integration rules.

Distributed transactions across contexts would introduce unacceptable coupling and availability risk. The platform needs reliable, asynchronous, idempotent event delivery with a clear consistency model.

## Decision

Adopt **event-driven integration** using the Outbox and Inbox patterns defined in the Enterprise Business Interaction Architecture:

- Every aggregate write commits its domain events to an Outbox in the same local transaction.
- Dispatchers publish from the Outbox to the bus/broker.
- Every consumer records processed events in an Inbox with a unique `(consumer_id, event_id)` constraint.
- Delivery is at-least-once; effect is exactly-once via idempotent processing.
- Events are past-tense, immutable, versioned facts.
- Correlation ID, causation ID, and distributed trace ID propagate through every event.

## Consequences

**Positive:**

- Local transactions per aggregate; no distributed locks.
- Reliable, replayable, auditable event stream.
- Consumers tolerate missing, duplicate, and out-of-order events.

**Negative:**

- Eventual consistency between contexts.
- Requires retry, dead-letter queue, and conflict-resolution infrastructure.

## Rationale

Outbox/Inbox is the established pattern for reliable event-driven integration without distributed transactions. It matches the platform's offline-first posture and the audit/trace requirements defined in Phase 3.2.
