# ADR-0002: Domain-Driven Design with Bounded Contexts

**Status:** Accepted
**Date:** 2026-08-01

## Context

The platform models a complex school management domain: academic structure, student lifecycle, attendance, assessment, certificates, finance, library, identity, notifications, workflow, security, reporting, and AI. Early code was feature-module oriented with cross-cutting table access and screen-to-database coupling (violations documented in `docs/architecture-compliance-report.md`).

A single shared domain model would create coupling and ambiguous ownership. The platform needs explicit context boundaries, aggregate roots, invariants, and a layered module structure.

## Decision

Adopt **Domain-Driven Design** with the bounded contexts defined in the Bounded Context Map. Each context owns its aggregate roots, invariants, repository contracts, and domain events. The Student Domain is the reference implementation standard (`docs/standards/student-domain-standard.md`).

Required per context:

- `application/`, `domain/`, `infrastructure/`, `presentation/`, `tests/` module layout.
- Dependency direction: `presentation -> application -> domain`, `infrastructure -> domain`.
- Aggregate-controlled mutation, value objects for validated concepts, past-tense events, policies, specifications, persistence-agnostic repository contracts.

## Consequences

**Positive:**

- Clear single source of truth per concept.
- Domain logic is isolated and testable without infrastructure.
- Integration boundaries are explicit.

**Negative:**

- More upfront discipline in module structure and contracts.
- Requires governance enforcement (naming, dependency rules).

## Rationale

DDD with bounded contexts directly addresses the ownership and coupling failures observed in early phases and is consistent with the Academic Domain Official Architecture and the Student Domain Standard already approved.
