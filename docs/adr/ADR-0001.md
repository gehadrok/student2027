# ADR-0001: Modular Monolith First, Future Microservice Extraction

**Status:** Accepted
**Date:** 2026-08-01

## Context

The Education ERP Platform spans 14 bounded contexts with different scaling and operational pressures. The natural future microservice boundaries were identified in the Bounded Context Map (Phase 3.1) — Academic Operations, Student Affairs, Attendance, Assessment, Finance, Library, Identity and Security, Communication, Workflow, Reporting and AI — with explicit splitting criteria.

Splitting immediately would introduce distributed-transaction, deployment, and operational complexity before the domain boundaries are proven in code. The platform currently operates as a single deployable with modular structure and a shared persistence abstraction.

## Decision

Adopt a **modular monolith** as the initial deployment topology. All bounded contexts live in one deployable, separated by module boundaries and enforced dependency rules. Extraction into microservices is deferred until a documented split criterion is met (independent deployment need, separate data ownership, high scaling pressure, external integration risk, distinct operational owner, stable published contracts).

The modular monolith still enforces:

- One concept, one owner (Bounded Context Map).
- Cross-context integration only through published contracts, events, and read models.
- Local transactions per aggregate; cross-context consistency via outbox/inbox and sagas.
- The dependency rules defined in `docs/governance/Architecture-Governance.md` §3.

## Consequences

**Positive:**

- Fast iteration and testing within a single deployable.
- Domain boundaries are proven in code before any split.
- Avoids premature distributed-transaction complexity.
- Shared Kernel and contracts remain enforceable.

**Negative:**

- Deployment scale and fault isolation are shared.
- A future split will require disciplined contract adherence today.

## Rationale

Microservices are a deployment and scaling strategy, not a modeling strategy. DDD bounded contexts can — and should — be implemented as a modular monolith first. The split criteria are already documented, so extraction can be data-driven rather than speculative.
